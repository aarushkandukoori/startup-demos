# Agent Trace Query Console

A fleet of 3,200 synthetic AI-agent runs (~19,500 spans) is generated in the
browser and loaded into a columnar store — one typed array per column, strings
dictionary-encoded. Filter the spans, watch the scan touch only the columns the
query mentions and report how long it actually took, group the results by any
dimension, run tunable evaluators over whole runs with a bootstrap interval on
the pass rate, and open any run as a span waterfall.

**Inspired by:** Laminar (laminar.sh) — "Open-source observability & evals for
AI agents — Rust backend, columnar analytics". An independent mini-demo built by
Aarush Kandukoori, inspired by Laminar's public product description. Not
affiliated with Laminar.

## How it works

**The store.** 16 columns, each a typed array of the same length: `trace_id`
(Int32), `kind`/`agent`/`model`/`env`/`version`/`status`/`error_type` (Uint8
dictionary codes), `name` (Uint16 dictionary code), `start_offset_ms`,
`duration_ms`, `cost_usd` (Float32), `input_tokens`, `output_tokens` (Int32).
Run-level attributes are denormalised onto every span, which is what makes the
wide layout pay off: a filter on `agent` or `model` never needs a join.

**The scan.** Each UI change runs `scanOnce`, a single pass that short-circuits
on the active predicates in order and appends surviving row indices to a
preallocated selection vector. A column is only dereferenced if a predicate or
the projection needs it, so "columns read: 4 / 16" is a statement about which
arrays the loop actually touched. The scan is timed with `performance.now()`
over 3 samples of 16 warm passes and the median is reported — that number is a
measurement of your browser, not a marketing figure. The bytes-read comparison
next to it is *arithmetic*, not a benchmark: touched columns × width × rows
versus the 37-byte full row a row-oriented layout would have to pull. The UI
says so on the page.

**The aggregates.** p50 and p95 come from sorting the selected durations, not
from a sketch: exact quantiles on a few thousand values are cheap and it keeps
the numbers auditable. Group-by builds one bucket per dictionary code, so
switching the dimension re-buckets from the same selection vector.

**The evaluators.** Four rule-based checks score a *run*, by walking that run's
span range in the columns:

- `latency_budget` — root-span wall-clock within a slider-set budget.
- `cost_ceiling` — summed span cost within a slider-set ceiling.
- `no_failed_step` — no span, retries included, ended in error or timeout.
- `grounded_answer` — a structural check on the span tree: if the run's last
  LLM span emitted more than 120 output tokens, some retrieval or search span
  must start before it. This is the shape of an offline check you can run over
  traces without a judge model, and it is deliberately naive.

The overall pass rate gets a 95% percentile bootstrap interval, resampling the
runs in the current slice with replacement (B chosen to cap the work, printed in
the UI, seeded so it does not jitter while you drag a slider). Turning an
evaluator off removes it from the conjunction and from every verdict.

**The waterfall.** Spans are laid out from `start_offset_ms` and `duration_ms`
relative to the root span, indented by depth, with retries labelled from the
`parent_span` column. Failed spans are red *and* carry their status and error
type as text.

## What's synthetic

Everything. There is no network call of any kind.

- Runs are generated by a seeded PRNG (mulberry32) from four agent templates —
  `support-triage`, `invoice-extract`, `code-review`, `web-research` — each a
  fixed sequence of steps with per-step probabilities, repeat counts, and one
  parallel batch (`web.search`).
- Model names (`atlas-70b`, `atlas-8b`, `orion-mini`), their prices, and their
  decode speeds are invented. They are not any vendor's real models, prices, or
  latencies. LLM span duration is `time-to-first-token + output_tokens ×
  ms/token`, multiplied by log-normal jitter; tool and retriever spans draw from
  per-step ranges with the same jitter.
- Failures are injected: per-step base rates scaled up in `staging` and on
  version `v1.4.2`, tool failures retried once as a nested child span, plus rare
  LLM timeouts and context-overflow errors that abort the run.
- Timestamps are offsets inside a synthetic six-hour window starting at 09:00;
  no real clock is read.
- The same seed loads on every visit, so the page always looks the same until
  you press "New sample".

Simplifications a real system would not make: the whole store lives in one
in-memory chunk with no row groups, no zone maps, no min/max pruning, no
compression, no time partitioning, and no vectorised or SIMD execution — the
scan is a scalar JavaScript loop. There is no ingestion path, no OTel semantics,
no sampling, no retention, and no model-graded evaluation; the evaluators here
are deterministic functions of the trace, which is the easy half of the problem.

## Run it

Open `index.html` in a browser. No build step, no dependencies, no network.
